# Patient consents

Open a patient and select **Consents**. Choose **New consent**, select a clinic template, review the automatically filled patient information and treating doctor, then edit the text for that patient. Save a draft or finalize the document. Finalization locks the wording; **Print** provides spaces for handwritten patient/guardian, doctor and optional witness/interpreter signatures. Finalized means the text is locked, not that a signature has been collected electronically.

Admin templates and patient drafts share a word processor with bold, italic, underline, strikethrough, font families, text sizes, colors, headings, bullets and numbering, alignment, indentation, RTL direction, undo/redo and expanded editing. English and Arabic versions are manually editable in separate tabs. Amiri is bundled for offline Arabic typography, alongside common system fonts. Clickable field labels insert atomic variables in templates and the patient's current values in patient drafts. Formatting is retained when saving, reopening and printing. Automatic translation is not included.

Under **Admin → Consents**, add templates, edit English/Arabic text, archive templates and optionally link them to procedures. Applying a linked procedure on the chart offers to create a consent, retaining the procedure, tooth labels and finding IDs. A template without procedure links remains available for manual selection. Multiple matching templates are offered together.

Template edits create a new revision. Saved patient documents retain their own text, original template revision and patient profile snapshot; they do not inherit subsequent universal edits. Simultaneous edits use revision checks. Drafts remain editable, while finalized documents are immutable. Archiving a template preserves existing patient records.

Seven original bilingual starter forms cover implants, fixed orthodontics, clear aligners, surgical extractions, root canal treatment, crowns/bridges and whitening. Their procedure categories reference the [Dentolize public consent generator](https://dentolize.com/tools/dental-consent-form-generator/); the starter text is original and should be reviewed by the clinic before clinical use.

Clinical reference checks include [Cambridge University Hospitals implant information](https://www.cuh.nhs.uk/patient-information/insertion-of-dental-implants/), [Leeds Teaching Hospitals orthodontic risks](https://www.leedsth.nhs.uk/services/orthodontic-dentistry/benefits-and-risks-of-orthodontic-dentistry/) and [AAE informed consent guidance](https://www.aae.org/specialty/clinical-resources/treatment-planning/informed-consent/).

Available template fields: `{{patient_name}}`, `{{patient_number}}`, `{{birth_date}}`, `{{phone}}`, `{{address}}`, `{{age}}`, `{{gender}}`, `{{doctor_name}}`, `{{date}}`, `{{procedure}}`, `{{details}}`. Formatted documents are stored as validated data with a plain-text fallback. Pasted content is sanitized; saved content is rendered through a strict format whitelist. The treating doctor defaults to the applied finding's doctor, the latest assigned doctor on the patient's chart, or the current user if they are a doctor. Another doctor can be selected, or a visiting doctor's name entered.

The `patient_consents` migration creates shared templates, patient records, narrow doctor lookup, row-level permissions, revision guards and Realtime publication entries. Clinical staff require Patients or Chart access; only active administrators can alter shared templates. Anonymous accounts have no access. Apply this migration before serving the updated frontend. The `consent_rich_documents` migration adds validated formatting data and an optional second patient-specific language version while preserving existing plain-text records and finalized-document locks. Apply both migrations before serving this frontend. New browser assets are included in the public asset build and service-worker shell.

In **Admin → Clinical procedures**, enable **Implant-specific procedure** and enter its default implant type. Implant procedures apply to whole teeth, enable progress tracking and automatically offer active implant consent templates, without requiring individual template links. The two existing Standard / Economic implant procedures are recognized automatically. **Implant Progress** accepts any implant type, retains the original procedure code when the type changes, and preserves that type on later chart updates.

In **Admin → Consents**, select **Implant consent with automatic cost section** as the form type. The bundled Dental implants template is upgraded to this type; its normal editable wording remains intact. The patient-specific form adds the **Ninth: Cost / تاسعا: التكلفة** paragraph in both languages, including the zirconia crown statement, implant count, per-implant fees, total and the type and tooth for each implant. The generated section appears under each language editor and is included in saved and printed documents.

Patient forms can assign one or more existing chart procedures. Implant forms require implant procedures with tooth numbers, fees (including zero if intended) and types. Choose **Two payments** or **Monthly installments**, the first-visit percentage, a restoration interval of 1–24 months and, for monthly payments, 1–60 installments. Defaults are two payments, 50% initially and restoration after four months. Monthly installments start one month after surgery; the last installment absorbs any cent rounding difference. Chart batch billing multipliers are respected. These consent terms do not create invoice payments or payment transactions.

Drafts retain their procedure and payment snapshots on reopening. **Refresh from chart** explicitly imports changed fees and implant types while preserving the patient's edited wording. Draft procedure assignments remain editable. Finalized forms retain their agreed text, procedure snapshots and payment settings permanently. Existing finalized forms are preserved by the migration.

Apply `supabase/migrations/20261025100120_implant_patient_consents.sql` after the two consent migrations and before deploying this frontend. It adds implant metadata to procedures, a template form type, validated patient assignment/payment snapshots, and retains the existing permissions, revision checks and finalized-document locks. The migration has been tested against local PostgreSQL fixtures; no hosted database changes are performed by the tests.
