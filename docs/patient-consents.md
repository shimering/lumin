# Patient consents

Open a patient and select **Consents**. Choose **New consent**, select a clinic template, review the automatically filled patient information and treating doctor, then edit the text for that patient. Save a draft or finalize the document. **Print** starts with the content written in the editor, followed by spaces for handwritten patient/guardian, doctor and optional witness/interpreter signatures. It does not prepend the consent title, patient summary, doctor summary or internal document metadata. Add any desired heading or identifying details within the document using the variable picker. The browser’s own date/site-title headers are controlled by its **Headers and footers** print setting. **Edit consent** reopens a finalized form as a draft, retaining its saved wording and settings. Save or finalize it again after editing. **Delete consent** is available for drafts and finalized forms, with a confirmation before permanent removal. Finalization records approval of the wording; signatures are collected on paper.

Admin templates and patient drafts share a word processor with bold, italic, underline, strikethrough, font families, text sizes, colors, headings, bullets and numbering, alignment, indentation, RTL direction, undo/redo and expanded editing. English and Arabic versions are manually editable in separate tabs. Amiri is bundled for offline Arabic typography, alongside common system fonts. Clickable field labels insert atomic variables in templates and the patient's current values in patient drafts. Formatting is retained when saving, reopening and printing. Automatic translation is not included.

Under **Admin → Consents**, add templates, edit English/Arabic text, archive templates and optionally link them to procedures. Applying a linked procedure on the chart offers to create a consent, retaining the procedure, tooth labels and finding IDs. A template without procedure links remains available for manual selection. Multiple matching templates are offered together.

Template edits create a new revision. Saved patient documents retain their own text, original template revision and patient profile snapshot; they do not inherit subsequent universal edits. Simultaneous edits use revision checks. Drafts remain editable. Finalized forms must be explicitly reopened before their wording can change. Reopening and deletion use the current revision to reject changes made from stale screens. Archiving a template preserves existing patient records.

Seven original bilingual starter forms cover implants, fixed orthodontics, clear aligners, surgical extractions, root canal treatment, crowns/bridges and whitening. Their procedure categories reference the [Dentolize public consent generator](https://dentolize.com/tools/dental-consent-form-generator/); the starter text is original and should be reviewed by the clinic before clinical use.

Clinical reference checks include [Cambridge University Hospitals implant information](https://www.cuh.nhs.uk/patient-information/insertion-of-dental-implants/), [Leeds Teaching Hospitals orthodontic risks](https://www.leedsth.nhs.uk/services/orthodontic-dentistry/benefits-and-risks-of-orthodontic-dentistry/) and [AAE informed consent guidance](https://www.aae.org/specialty/clinical-resources/treatment-planning/informed-consent/).

Core template fields: `{{patient_name}}`, `{{patient_number}}`, `{{birth_date}}`, `{{phone}}`, `{{address}}`, `{{age}}`, `{{gender}}`, `{{doctor_name}}`, `{{date}}`, `{{procedure}}`, `{{details}}`. Formatted documents are stored as validated data with a plain-text fallback. Pasted content is sanitized; saved content is rendered through a strict format whitelist. The treating doctor defaults to the applied finding's doctor, the latest assigned doctor on the patient's chart, or the current user if they are a doctor. Another doctor can be selected, or a visiting doctor's name entered.

The `patient_consents` migration creates shared templates, patient records, narrow doctor lookup, row-level permissions, revision guards and Realtime publication entries. Clinical staff require Patients or Chart access; only active administrators can alter shared templates. Anonymous accounts have no access. Apply this migration before serving the updated frontend. The `consent_rich_documents` migration adds validated formatting data and an optional second patient-specific language version while preserving existing plain-text records and finalized-document controls. Apply both migrations before serving this frontend. New browser assets are included in the public asset build and service-worker shell.

In **Admin → Clinical procedures**, enable **Implant-specific procedure** and enter its default implant type. Implant procedures apply to whole teeth, enable progress tracking and automatically offer active implant consent templates, without requiring individual template links. The two existing Standard / Economic implant procedures are recognized automatically. **Implant Progress** accepts any implant type, retains the original procedure code when the type changes, and preserves that type on later chart updates.

In **Admin → Consents**, select **Implant consent with fee variables** as the form type. The bundled Dental implants template is upgraded to this type; its normal editable wording remains intact. Use the editor’s variable picker to insert the implant count, types, teeth, unit price, total, per-tooth implant details, payment arrangement, first-visit fee method, percentage or amount, restoration interval, balance and monthly installment values wherever needed. No cost heading or paragraph is added automatically. Existing cost paragraphs remain ordinary editable content when an older form is reopened.

Patient forms can assign one or more existing chart procedures. Implant forms require implant procedures with tooth numbers, fees (including zero if intended) and types. Choose **Two payments** or **Monthly installments**, a first-visit percentage or fixed amount, a restoration interval of 1–24 months and, for monthly payments, 1–60 installments. Defaults are two payments, 50% initially and restoration after four months. A fixed first-visit amount must be nonnegative and cannot exceed the total implant fee. Monthly installments start one month after surgery; the last installment absorbs any cent rounding difference. Chart batch billing multipliers are respected. These consent terms do not create invoice payments or payment transactions.

The patient settings supply the variable values. In templates, variables are atomic field labels. In patient drafts, they become editable inline text; untouched occurrences update when their source values change, while directly edited occurrences become custom text. Repeated occurrences are tracked separately. Arabic and English editors use their own localized values. Financial variables in a standard template also activate the implant settings when preparing the patient form.

**Treating doctor (Arabic)** uses `{{doctor_name_ar}}`. Enter the Arabic name in the patient consent form; it is saved with that consent and can be placed anywhere in either language. An Arabic doctor display name is used as an initial value when available.

Drafts retain their procedure and payment snapshots on reopening. **Refresh from chart** explicitly imports changed fees and implant types while preserving the patient's edited wording. Draft procedure assignments remain editable. Finalized forms retain their agreed text, procedure snapshots and payment settings until staff explicitly reopen or delete them. Existing finalized forms are preserved by the migrations.

Apply `supabase/migrations/20261025100120_implant_patient_consents.sql` after the two consent migrations and before deploying this frontend. It adds implant metadata to procedures, a template form type, validated patient assignment/payment snapshots, and retains the existing permissions, revision checks and finalized-document controls. The migration has been tested against local PostgreSQL fixtures; no hosted database changes are performed by the tests.

The editor toolbar includes **Insert table**. New tables start with two rows and two columns. Select a cell to show row/column actions, blue drag handles, and **+** buttons after the final row and column. Drag the upper handles to change column width and the side handles to change row height; focused handles also support arrow-key adjustments. Tables can be edited in either language and in expanded mode. Selecting a word shows its actual font size, including inherited sizes; changing the size applies only to the selection. **Fit row to text** enables automatic row height, so a row shrinks or grows with its words. Dragged heights can be reduced to 16px, with the cell content determining the visible minimum. Cell formatting, column widths and row heights survive saving and reopening. Printed tables retain their column proportions and fit the available page width.

Apply `supabase/migrations/20261025120548_consent_editing_tables_and_fixed_fees.sql` before deploying the table editor, finalized-form controls and fixed-amount payments. The migration extends the existing document whitelist and payment validation, permits explicit reopening without changing saved text in the same request, and grants deletion only through the existing patient/chart permissions.

Apply `supabase/migrations/20261025131539_consent_flexible_variables.sql` before deploying flexible variables. It extends the validated variable whitelist and inline binding metadata, and adds the saved Arabic doctor-name field. It does not rewrite existing consent documents.
