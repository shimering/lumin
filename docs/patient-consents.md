# Patient consents

Each patient draft includes **Page layout & clinic logo**. The clinic logo is visible above the editable wording. Include or hide it, set its width and left/center/right position, add space above it, and choose **First page only** or **Every page**. The same panel offers no frame, a single line, double lines or rounded corners, plus top/bottom/left/right margins in millimeters. Framed pages retain at least 8 mm of inner space. The A4 paper preview updates while editing; each printed/PDF page uses the selected frame and physical margins. The image itself is shared with **Admin → Print form**.

Page-layout choices are saved in the consent's `print_layout` snapshot. An empty snapshot inherits clinic defaults. Reopening a draft retains its own choices; finalized forms display the saved layout with disabled controls and must be reopened before it can change. Clinic-wide print settings remain the defaults for other consents.

Palmer labels in procedure choices, inserted tooth variables and rich consent text use the dental chart's SVG bracket geometry with isolated left-to-right layout, so Arabic does not flip a quadrant. Editable tooth symbols are atomic and retain their plain-text labels when saved. Untouched variable occurrences still follow the assigned teeth; manual changes remain patient-specific. English, Arabic and printed versions use the same symbols.

Apply `supabase/migrations/20261026081901_consent_page_layout_and_palmer.sql` after the existing consent migrations before serving the updated assets. It adds the validated layout snapshot and permitted Palmer tooth values, retains patient access policies and finalized-form guards, and does not rewrite saved consent wording. Local PostgreSQL checks cover invalid layouts, unsafe symbols, access revocation and finalized layout protection. Browser checks in `tests/consent-layout-print-browser.test.cjs` cover native/iPad pagination, per-page frames, physical margins and first/all/hidden logos; rendered-page checks verify logo pixels are absent on the excluded pages.

Open a patient and select **Consents**. Choose **New consent**, select a clinic template, review the automatically filled patient information and treating doctor, then edit the text for that patient. Save a draft or finalize the document. **Print** starts with the content written in the editor, followed by spaces for handwritten patient/guardian, doctor and optional witness/interpreter signatures. It does not prepend the consent title, patient summary, doctor summary or internal document metadata. Add any desired heading or identifying details within the document using the variable picker. The dedicated print layout suppresses the browser’s default date, site title, URL and page numbers and supports clinic letterhead configured in Admin. **Edit consent** reopens a finalized form as a draft, retaining its saved wording and settings. Save or finalize it again after editing. **Delete consent** is available for drafts and finalized forms, with a confirmation before permanent removal. Finalization records approval of the wording; signatures are collected on paper.

Admin templates and patient drafts share a word processor with bold, italic, underline, strikethrough, font families, text sizes, colors, headings, bullets and numbering, alignment, indentation, RTL direction, undo/redo and expanded editing. English and Arabic versions are manually editable in separate tabs. Amiri is bundled for offline Arabic typography, alongside common system fonts. Clickable field labels insert atomic variables in templates and the patient's current values in patient drafts. Formatting is retained when saving, reopening and printing. Automatic translation is not included.

Under **Admin → Consents**, add templates, edit English/Arabic text, archive templates and optionally link them to procedures. Applying a linked procedure on the chart offers to create a consent, retaining the procedure, tooth labels and finding IDs. A template without procedure links remains available for manual selection. Multiple matching templates are offered together.

Template edits create a new revision. Saved patient documents retain their own text, original template revision and patient profile snapshot; they do not inherit subsequent universal edits. Simultaneous edits use revision checks. Drafts remain editable. Finalized forms must be explicitly reopened before their wording can change. Reopening and deletion use the current revision to reject changes made from stale screens. Archiving a template preserves existing patient records.

Seven original bilingual starter forms cover implants, fixed orthodontics, clear aligners, surgical extractions, root canal treatment, crowns/bridges and whitening. Their procedure categories reference the [Dentolize public consent generator](https://dentolize.com/tools/dental-consent-form-generator/); the starter text is original and should be reviewed by the clinic before clinical use.

Clinical reference checks include [Cambridge University Hospitals implant information](https://www.cuh.nhs.uk/patient-information/insertion-of-dental-implants/), [Leeds Teaching Hospitals orthodontic risks](https://www.leedsth.nhs.uk/services/orthodontic-dentistry/benefits-and-risks-of-orthodontic-dentistry/) and [AAE informed consent guidance](https://www.aae.org/specialty/clinical-resources/treatment-planning/informed-consent/).

Core template fields: `{{patient_name}}`, `{{patient_number}}`, `{{birth_date}}`, `{{phone}}`, `{{address}}`, `{{age}}`, `{{gender}}`, `{{doctor_name}}`, `{{date}}`, `{{procedure}}`, `{{details}}`. Formatted documents are stored as validated data with a plain-text fallback. Pasted content is sanitized; saved content is rendered through a strict format whitelist. The treating doctor defaults to the applied finding's doctor, the latest assigned doctor on the patient's chart, or the current user if they are a doctor. Another doctor can be selected, or a visiting doctor's name entered.

The `patient_consents` migration creates shared templates, patient records, narrow doctor lookup, row-level permissions, revision guards and Realtime publication entries. Clinical staff require Patients or Chart access; only active administrators can alter shared templates. Anonymous accounts have no access. Apply this migration before serving the updated frontend. The `consent_rich_documents` migration adds validated formatting data and an optional second patient-specific language version while preserving existing plain-text records and finalized-document controls. Apply both migrations before serving this frontend. New browser assets are included in the public asset build and service-worker shell.

In **Admin → Clinical procedures**, enable **Implant-specific procedure** and enter its default implant type. Implant procedures apply to whole teeth, enable progress tracking and automatically offer active implant consent templates, without requiring individual template links. The two existing Standard / Economic implant procedures are recognized automatically. **Implant Progress** accepts any implant type, retains the original procedure code when the type changes, and preserves that type on later chart updates.

In **Admin → Consents**, select **Implant consent with fee variables** as the form type. The bundled Dental implants template is upgraded to this type; its normal editable wording remains intact. Use the editor’s variable picker to insert the implant count, types, teeth, unit price, total, per-tooth implant details, payment arrangement, first-visit fee method, percentage or amount, restoration interval, balance and monthly installment values wherever needed. No cost heading or paragraph is added automatically. Existing cost paragraphs remain ordinary editable content when an older form is reopened.

Patient forms can assign one or more existing chart procedures. Implant forms require implant procedures with tooth numbers, fees (including zero if intended) and types. Choose **Two payments** or **Monthly installments**, a first-visit percentage or fixed amount, a restoration interval of 1–24 months and, for monthly payments, 1–60 installments. Defaults are two payments, 50% initially and restoration after four months. A fixed first-visit amount must be nonnegative and cannot exceed the total implant fee. Monthly installments start one month after surgery; the last installment absorbs any cent rounding difference. Chart batch billing multipliers are respected. These consent terms do not create invoice payments or payment transactions.

The patient settings supply the variable values. In templates, variables are atomic field labels. In patient drafts, they become editable inline text; untouched occurrences update when their source values change, while directly edited occurrences become custom text. Repeated occurrences are tracked separately. Arabic and English editors use their own localized values. Financial variables in a standard template also activate the implant settings when preparing the patient form.

**Treating doctor (Arabic)** uses `{{doctor_name_ar}}`. Enter the Arabic name in the patient consent form; it is saved with that consent and can be placed anywhere in either language. An Arabic doctor display name is used as an initial value when available.

Drafts retain their procedure and payment snapshots on reopening. **Refresh from chart** explicitly imports changed fees and implant types while preserving the patient's edited wording. Draft procedure assignments remain editable. Finalized forms retain their agreed text, procedure snapshots and payment settings until staff explicitly reopen or delete them. Existing finalized forms are preserved by the migrations.

Apply `supabase/migrations/20261025100120_implant_patient_consents.sql` after the two consent migrations and before deploying this frontend. It adds implant metadata to procedures, a template form type, validated patient assignment/payment snapshots, and retains the existing permissions, revision checks and finalized-document controls. The migration has been tested against local PostgreSQL fixtures; no hosted database changes are performed by the tests.

The editor toolbar includes **Insert table**. New tables start with two rows and two columns. Select a cell to show row/column actions, blue drag handles, and **+** buttons after the final row and column. Drag the upper handles to change column width and the side handles to change row height; focused handles also support arrow-key adjustments. Tables can be edited in either language and in expanded mode. Selecting a word shows its actual font size, including inherited sizes; changing the size applies only to the selection. **Fit row to text** enables automatic row height, so a row shrinks or grows with its words. Dragged heights can be reduced to 16px, with the cell content determining the visible minimum. Cell formatting, column widths and row heights survive saving and reopening. Printed tables retain their column proportions and fit the available page width.

Apply `supabase/migrations/20261025120548_consent_editing_tables_and_fixed_fees.sql` before deploying the table editor, finalized-form controls and fixed-amount payments. The migration extends the existing document whitelist and payment validation, permits explicit reopening without changing saved text in the same request, and grants deletion only through the existing patient/chart permissions.

Apply `supabase/migrations/20261025131539_consent_flexible_variables.sql` before deploying flexible variables. It extends the validated variable whitelist and inline binding metadata, and adds the saved Arabic doctor-name field. It does not rewrite existing consent documents.

Printing uses a standalone document, independent of app zoom, viewport widths and modal overflow, and waits for its styles and used fonts before opening the print dialog. Arabic PDF regressions cover desktop/mobile viewports and app scaling; set `LUMIN_PDF_PYTHON` to Python with pypdf, and optionally `LUMIN_PDFTOPPM` to Poppler for rendered-page ink checks when running `tests/consent-print-browser.test.cjs`.

Apply `supabase/migrations/20261025202900_consent_compact_table_rows.sql` before deploying automatic or compact row heights. Existing document content and dimensions are preserved.


Consent printing opens a separate print-only document and keeps it available after `afterprint`, since Android can report that event before its native preview captures the page. No editor controls are included. Zero `@page` margins remove automatic browser date/title/URL/page-number decorations in the normal browser print layout; content retains its own inner gutters. A4 and Letter regression PDFs verify Arabic text, app zoom independence, repeated clinic headers/footers and nonblank pages.

Admin → Consent templates → Consent print layout controls bilingual header/footer text, their font sizes and minimum heights, clinic-logo visibility/width/alignment, and the signature section. The image is read from the existing Admin Print form logo setting. The new `consent_print_settings` singleton is readable by active clinical staff and writable only by active administrators, with database bounds and optimistic update checks. Apply `20261025212806_consent_line_spacing.sql` before publishing these assets; it also adds validated paragraph line spacing (1–3) to saved consent documents. The editor's Line spacing selector applies to the current or selected paragraphs and survives template, patient-draft and print rendering.

Popup backdrops suppress touch scrolling and drag-generated clicks, so swiping outside a dialog cannot dismiss it or navigate the patient workspace. Scrolling and text/table gestures inside remain available. Deliberate backdrop taps retain the dialog’s existing close behavior; Close/Cancel retains its unsaved-change confirmation. Patient swipe Back also rechecks open dialogs at release and before navigation.

Unsaved consent changes use an in-dialog confirmation. Cancel (or Escape) restores the same mounted editor and field values; only Discard changes closes the form or resumes the requested navigation. A cancelled exit does not invalidate pending consent requests or clear editing state.

Opening a patient draft or finalized consent selects Arabic when an Arabic version is available, including when the application UI is English. English remains selectable, and the selected version stays selected during save and background refresh. English-only records retain their available version. This changes viewing defaults without rewriting the saved primary language or either document's text.

Returning from the print tab triggers the usual foreground data/access catch-up. That refresh now retains the same consent dialog, editor instance, unsaved text, field values and selected language when the user, patient and consent permissions still match. Sign-out, an account/patient change, permission revocation or explicit navigation still close the previous dialog.

The consent print tab owns its print action. On desktop and Android, automatic printing waits until that tab is visible and its fonts/images are ready, and the persistent Print / Save as PDF button calls the browser print API synchronously from a tap. On iPad/iPhone (including iPadOS's desktop identity and home-screen mode), the tab prepares an A4 PDF locally before enabling **Open PDF to print**. Tap it, then use the PDF viewer's **Share → Print** action. No share API is invoked by Lumin and no consent data is uploaded for PDF preparation. The original consent and print tab remain available after closing the PDF, and the action can be repeated.

The iPad PDF uses the same formatted HTML, selected fonts, font sizes, line spacing, preserved inline spaces, column widths and row heights as the consent document. Small tables keep their saved width; oversized tables fit the available sheet width proportionally. Rows can grow to accommodate their text. Each PDF page is rendered separately with a repeated clinic header/footer, with page boundaries between blocks or complete text lines. The raster canvas is capped below three megapixels and released after each page to limit tablet memory use. Bundled html2canvas and pdf-lib assets are included in the offline shell. The screen-only toolbar is excluded from paper/PDF output. Back to consent returns to the original editor. On desktop/Android, manual printing cancels queued automatic requests to avoid two print dialogs.

When printing an open consent, the print tab receives a sanitized snapshot of its displayed content with measured text styles, paragraph/list margins, indentation, table widths, column ratios, cell padding and row sizing. Editor chrome, editable attributes and event handlers are excluded. The same snapshot supplies native printing and the iPad PDF; it does not rebuild the visible draft with a separate set of print text defaults. Table widths are initialized synchronously, so printing directly from history cannot capture a transient full-width table. The record-based renderer remains the fallback when there is no mounted source. `tests/consent-draft-print-match-browser.test.cjs` compares the actual draft and print geometry in English and Arabic; set `LUMIN_TEST_APPLE_TOUCH=1` to also generate and inspect the iPad snapshot PDF.

`tests/consent-ipad-print-browser.test.cjs` verifies Arabic and English iPad identities, local PDF generation, A4 dimensions, saved table and text metrics, overflow protection, and repeat opening without external requests. Set `LUMIN_TEST_WEBKIT_PATH` to a WebKit runner to check rendering and the direct-tap link action in that engine; the Windows WebKit runner does not include iPad Safari's native PDF viewer. Physical iPad/AirPrint validation is still required for the final native printer selection.
